#### 5.2.1 故障案例：2026-02-05 飞书消息无响应

**故障现象：**
- 飞书发送消息无 AI 响应
- 网关端口 18789 未监听

**根因分析：**
1. **直接原因**: 网关进程未运行
2. **配置错误**: `openclaw.json` 中 `plugins.entries.feishu` 被错误添加
3. **错误来源**: `openclaw doctor --fix` 自动修复时误将 feishu channel 当作 plugin 添加到 `plugins.entries`

**关键区分：**
- `channels.feishu` ✓ 正确 - feishu 是内置 channel，配置在这里
- `plugins.entries.feishu` ✗ 错误 - feishu 不是独立 plugin，不应出现在这里

**修复步骤：**
```bash
# 1. 检查当前配置
type %USERPROFILE%\.openclaw\openclaw.json | findstr "plugins"

# 2. 如果看到 plugins.entries.feishu，需要移除
# 编辑 openclaw.json，将 plugins.entries 设为空对象: {}

# 3. 启动网关
cd D:\openclaw && node openclaw.mjs gateway --port 18789

# 4. 验证端口
netstat -ano | findstr "18789"
```

**教训：**
- 运行 `openclaw doctor --fix` 后必须检查配置是否被错误修改
- feishu/lark/discord/telegram/slack 等都是 channel，不是 plugin

#### 5.2.2 故障案例：2026-02-06 Control UI 构建失败 + Token 认证

**故障现象：**
- 网关启动时报 `Control UI build failed: Missing UI runner: install pnpm, then retry.`
- Control UI 页面打开后显示 "Disconnected from gateway" + "gateway token missing"

**根因分析：**
1. **UI 构建失败**: 系统未安装 `pnpm`，网关无法构建 Control UI 前端资源
2. **PATH 问题**: `npm install -g pnpm` 安装到 `%APPDATA%\npm\`，但 Git Bash 的 PATH 未包含该目录
3. **Token 缺失**: 直接访问 `/__openclaw__/` 不带 token，WebSocket 连接被拒绝

**修复步骤：**
```bash
# 1. 安装 pnpm
npm install -g pnpm

# 2. 确保 PATH 包含 npm 全局目录（Git Bash 环境）
export PATH="$PATH:/c/Users/刘方林/AppData/Roaming/npm"

# 3. 重启网关（会自动构建 Control UI）
cd D:\openclaw && node openclaw.mjs gateway --port 18789

# 4. 用带 token 的 URL 访问管理界面
openclaw dashboard          # 自动打开浏览器
openclaw dashboard --no-open # 仅打印 URL
# URL 格式: http://127.0.0.1:18789/?token=<your-token>
```

**教训：**
- Git Bash 环境的 PATH 可能不包含 Windows npm 全局目录，需手动添加
- Control UI 访问必须带 token，使用 `openclaw dashboard` 命令最方便
- Control UI 构建失败不影响核心功能（飞书消息、插件等正常工作）

#### 5.2.3 故障案例：2026-02-25 MiniMax API 401 认证错误

**故障现象：**
- 飞书发送消息返回 HTTP 401 认证错误
- 错误信息：`login fail: Please carry the API secret key in the 'Authorization' field of the request header`
- 切换模型时出现此问题

**根因分析（历时 3 小时深度调试）：**
1. **主要根因**: Claude Code 插件设置了环境变量 `ANTHROPIC_AUTH_TOKEN`（你的 Claude API key）
2. **SDK 行为**: Anthropic SDK 会自动读取该环境变量并添加 `Authorization: Bearer` header
3. **认证冲突**: 当 OpenClaw 调用 MiniMax API 时，SDK 同时发送：
   - `X-Api-Key: sk-api-xxx`（MiniMax key）
   - `Authorization: Bearer `（空 token，来自空字符串的 ANTHROPIC_AUTH_TOKEN）
4. **认证失败**: MiniMax API 优先使用 `Authorization` header，看到空 token 返回 401

**关键调试发现：**
- `ANTHROPIC_AUTH_TOKEN` 设置为空字符串时，SDK 的 `bearerAuth` 检查 `if (this.authToken == null)` 返回 false（因为 `"" != null`）
- 导致 SDK 发送 `Authorization: Bearer ` 而非完全不发送该 header

**配置叠加问题：**
- 使用了错误的 provider：`minimax`（国际版 baseUrl: `api.minimax.io`）而非 `minimax-cn`（中国区 baseUrl: `api.minimaxi.com`）
- 你的 MiniMax API key 只在 `api.minimaxi.com` 上有效

**修复步骤：**
```bash
# 1. 修改 pi-ai 库，禁用 Authorization header
# 文件：D:\openclaw\node_modules\@mariozechner\pi-ai\dist\providers\anthropic.js
# 在 createClient 函数的 API key auth 分支中添加 authToken: null

# 2. 重新配置 MiniMax 中国区 provider
cd D:\openclaw
node openclaw.mjs onboard --auth-choice minimax-api-key-cn \
  --minimax-api-key "sk-api-你的key" --non-interactive --accept-risk

# 3. 重启网关
taskkill //F //IM node.exe
node openclaw.mjs gateway --port 18789

# 4. 验证
node openclaw.mjs agent --agent leo-assistant --message "测试"
```

**避免重复出现的措施：**
1. **不要在运行 OpenClaw 的环境中设置 `ANTHROPIC_AUTH_TOKEN`**
   - Claude Code 插件设置的环境变量会传递给 OpenClaw
   - 使用 `--local` 模式测试可避免此问题

2. **中国区用户使用 `minimax-cn` provider**
   - 配置命令：`--auth-choice minimax-api-key-cn`

3. **详细运维日志**：`docs/openclaw_operations/OPERATIONS_LOG_20260225.md`

**教训：**
- 第三方 SDK 的环境变量自动读取机制可能导致跨服务认证冲突
- 空字符串不等于 null，需要显式处理
- 调试 API 认证问题时，使用 `--local` 模式并添加 SDK 层日志

### 5.3 配置保护规则

**绝对禁止**：
1. 不要在飞书对话中请求 AI 修改 OpenClaw 配置
2. 不要手动添加 `mcpTools`, `systemPrompt`, `cron`, `schedules` 到 openclaw.json
3. 不要在 plugins.entries 中添加 channel 类型（如 feishu、lark、discord、telegram、slack 等）

**危险操作警告**：
- ⚠️ 运行 `openclaw doctor --fix` 后必须人工检查配置
  - doctor 可能会错误地将 channel 添加到 `plugins.entries`
  - 修复后需验证: `plugins.entries` 应该为空 `{}` 或只包含真正的插件

**Channel vs Plugin 区分表：**

| 类型 | 示例 | 配置位置 | 说明 |
|------|------|----------|------|
| Channel | feishu, lark, discord, telegram, slack, whatsapp, teams | `channels.{name}` | 内置消息渠道 |
| Plugin | leo-system, memory-core, bluebubbles | `plugins.entries.{name}` | 外部扩展插件 |

**配置验证清单：**
```bash
# 1. 检查是否有错误的 plugin 配置
type %USERPROFILE%\.openclaw\openclaw.json | findstr "plugins"

# 2. 正确的 plugins.entries 应该是以下之一：
#    - "entries": {}  （空对象）
#    - "entries": {"leo-system": {"enabled": true}}  （仅真正插件）

# 3. 如果出现 feishu/discord/telegram 等，立即删除
```

**定时任务正确配置方式**：

```bash
openclaw cron list   # 查看所有定时任务

```

**安全修改流程**：
```bash

copy %USERPROFILE%\.openclaw\openclaw.json openclaw.json.backup

# 2. 编辑配置后立即重启
```

|------|---------------------|-----------------|
| **底层模型** | Claude Opus 4.6 | GPT-5.3-Codex |
| **核心优势** | 深度推理、架构设计、代码审查、上下文理解 | 快速生成、批量操作、脚手架搭建、并行执行 |
| **上下文窗口** | 200K 令牌 | 400K 令牌 |
| **工作风格** | 先想清楚再动手，"三思而后行" | 快速出活，"先跑起来再说" |
| **适合场景** | 复杂决策、重构、审查、规划 | 新建文件、模板生成、重复性修改 |
| **配置文件** | `CLAUDE.md`（本文件） | `.codex/` 目录或 `AGENTS.md` |

### 8.2 协作工作流（5 步法）

```
步骤1: Claude Code 规划
  ↓ 输出：任务计划（task_plan.md 或 TODO 列表）
步骤2: Claude Code 拆解任务
  ↓ 输出：具体的文件清单 + 每个文件要做什么
步骤3: Codex 批量执行
  ↓ 输出：新建/修改的代码文件
步骤4: Claude Code 审查验收
  ↓ 输出：审查意见、修改建议
步骤5: Claude Code 收尾提交
  ↓ 输出：Git 提交、文档更新
```

**简单记忆**：Claude 想 → Claude 拆 → Codex 干 → Claude 查 → Claude 收

### 8.3 任务分配规则

#### 交给 Claude Code（大脑）的任务：

| 任务类型 | 举例 |
|---------|------|
| 架构设计 | "这个功能应该怎么设计？放在哪个模块？" |
| 代码审查 | "检查 Codex 生成的代码有没有问题" |
| 复杂重构 | "把这个模块从单体拆成微服务" |
| Bug 诊断 | "为什么这个功能不工作？根因是什么？" |
| 规划决策 | "接下来应该先做什么？优先级怎么排？" |
| 文档编写 | "写技术方案、更新 CLAUDE.md" |
| 上下文管理 | "读取系统记忆、更新进度文件" |

#### 交给 Codex（脚手架）的任务：

| 任务类型 | 举例 |
|---------|------|
| 脚手架搭建 | "按这个结构新建 5 个文件" |
| 模板生成 | "根据模板批量生成 SKILL.md" |
| 批量修改 | "把所有文件里的 old_name 改成 new_name" |
| 快速原型 | "快速搭一个 Flask API 的基本框架" |
| 重复性工作 | "给这 10 个技能都加上 __init__.py" |
| 测试生成 | "根据这个函数生成单元测试" |
| 样板代码 | "生成标准的 CRUD 接口代码" |

### 8.4 文件交接协议

> 两个引擎通过**文件系统**交接信息，不需要互相"对话"。

| 交接方式 | 说明 | 示例 |
|---------|------|------|
| **任务文件** | Claude Code 写任务说明，Codex 读取执行 | `docs/planning/task_plan.md` |
| **代码文件** | Codex 生成代码，Claude Code 审查 | `src/` 目录下的代码文件 |
| **配置文件** | 共享项目配置，两者都能读写 | `CLAUDE.md`、`AGENTS.md` |
| **进度文件** | 记录谁做了什么 | `docs/progress/progress.md` |

**交接流程**：
1. Claude Code 在 `task_plan.md` 中写清楚要做什么
2. 用户切换到 Codex，告诉它"按照 task_plan.md 执行"
3. Codex 执行完毕后，用户切回 Claude Code
4. Claude Code 审查 Codex 的产出，提出修改意见

### 8.5 质量保障机制

| 环节 | 负责人 | 检查内容 |
|------|--------|---------|
| **事前** | Claude Code | 任务拆解是否合理、需求是否明确 |
| **事中** | Codex | 代码是否能运行、文件结构是否正确 |
| **事后** | Claude Code | 代码质量、安全性、命名规范、架构一致性 |

**Claude Code 审查 Codex 产出时的检查清单**：
- [ ] 命名是否符合 snake_case 规范
- [ ] 代码注释是否使用中文
- [ ] 是否引入了安全漏洞
- [ ] 是否与现有架构一致
- [ ] 是否有重复代码（去重检查）
- [ ] 文件是否放在了正确的目录

### 8.6 冲突避免规则

**绝对禁止**：
1. 两个引擎**不要同时编辑同一个文件** — 会导致冲突覆盖
2. Codex **不要修改** `CLAUDE.md`、`shared_memory.md` 等系统核心文件 — 这些由 Claude Code 独占管理
3. Claude Code **不要做**大量重复性的文件创建 — 这是 Codex 的活
4. **不要让 Codex 做架构决策** — 它擅长执行，不擅长决策

**安全操作顺序**：
```
1. 确认当前没有未保存的修改（git status）
2. 明确当前由哪个引擎在工作
3. 一个引擎完成后，另一个再接手
4. 接手前先检查文件状态
```

## 9. 🌐 简体中文交互规则（强制）

> **⚠️ 强制执行**：用户是技术初学者，所有 AI 交互必须使用简体中文，降低理解门槛。

### 9.1 语言规则

| 场景 | 规则 | 示例 |
|------|------|------|
| **AI 回复** | 全部使用简体中文 | "已完成文件创建" 而不是 "File created" |
| **代码注释** | 使用中文注释 | `# 获取用户列表` 而不是 `# Get user list` |
| **错误说明** | 用中文解释错误原因和解决方法 | "端口被占用，需要先关闭旧进程" |
| **技术术语** | 保留英文原词，但括号内附中文解释 | "使用 API（应用程序接口）调用" |
| **文件名/变量名** | 保持英文（Python 规范要求） | `weekly_report_skill.py` |
| **Git 提交信息** | 使用中文 | `feat: 新增周报生成技能` |

### 9.2 技术术语对照表（常用）

| 英文术语 | 中文解释 | 使用场景 |
|---------|---------|---------|
| Skill（技能） | 系统的一个独立能力模块 | 技能开发 |
| Agent（代理） | 能自主执行任务的 AI 助手 | 任务分配 |
| Workflow（工作流） | 多个步骤串起来的自动化流程 | 流程编排 |
| Pipeline（流水线） | 数据或任务从头到尾的处理链条 | 内容生产 |
| Scaffold（脚手架） | 快速搭建项目基本结构的工具 | 项目初始化 |
| Refactor（重构） | 不改功能，只优化代码结构 | 代码优化 |
| Deploy（部署） | 把代码放到服务器上运行 | 上线发布 |
| Debug（调试） | 找到并修复代码里的错误 | 问题排查 |
| Context（上下文） | AI 当前能"看到"的所有信息 | 记忆管理 |
| Token（令牌） | AI 处理文本的最小单位，约等于一个汉字 | 成本计算 |
| Hook（钩子） | 在特定时机自动触发的脚本 | 自动化 |
| MCP（模型上下文协议） | 让 AI 工具之间互相通信的标准 | 工具集成 |
| Gateway（网关） | 消息的统一入口和分发中心 | OpenClaw |
| Channel（渠道） | 消息来源平台（如飞书、微信） | 消息路由 |
| Plugin（插件） | 给系统增加新功能的扩展模块 | 功能扩展 |

### 9.3 回复风格要求

- 用**大白话**解释技术概念，避免堆砌术语
- 给出**可以直接复制执行**的命令，不要让用户自己拼
- 操作步骤用**数字编号**，一步一步来
- 遇到错误时，先说**怎么解决**，再解释为什么出错
- 总结用**一两句话**，不要写长篇大论
